## State-of-the-art ASR for low-resource & multilingual speech (Kurdish-Sorani / Central Kurdish, ckb_Arab), on-device desktop, mid-2026.

Cortex already bet on the right base model. Meta's Omnilingual ASR (released Nov 2025, arXiv 2511.09690, Apache-2.0) is the only frontier system that explicitly covers Central Kurdish (ckb_Arab) and the surrounding Arabic-script Kurdish varieties, and its published per-language results give Cortex exactly the proof point it is missing: the 7B LLM-ASR reaches CER 6.0 on Central Kurdish with only 59.6 training hours, and CER 1.2/0.4/3.4 on Northern Kurdish (Arabic/Cyrillic/Latin). No competitor comes close on coverage: NVIDIA Parakeet-TDT-0.6B-v3 and Canary-1B-v2 only do 25 European languages (no Kurdish, no Arabic script); Qwen3-ASR covers 52 languages but not Kurdish and ships closed weights for the flagship; Whisper large-v3 technically supports ckb but Cortex's current samil24 Sorani fine-tune is unbenchmarked and the Whisper path was already slated for removal. The on-device tension is real: the 300M-CTC variant Cortex has wired runs at ~0.22 RTF in ~2 GiB and ~348 MB int8 (great for a desktop app) but trails the LLM variants in accuracy; the 7B-LLM needs ~15 GiB VRAM and is not desktop-viable. The winning architecture is therefore a two-tier setup: ship Omnilingual CTC-300M/1B int8 via sherpa-onnx as the always-on on-device engine, and LoRA-fine-tune it on Cortex's own curated Sorani data to close the gap to the 7B teacher. The single most important move for the "proven accuracy 2 -> 10" jump is not a new model at all: it is running the existing eval.rs gold-set harness against Omnilingual and PUBLISHING the WER/CER, because the eval infrastructure (holdout gold segments, WER/CER, DPO export) already exists and is the exact thing buyers and the scorecard are penalizing as "zero published numbers."

**Turn the Disagreement Refinery + DPO export into a noisy-student pseudo-labeling flywheel**  
Cortex's tiered jury (T0 gate -> T1 judge -> T2 listener -> debate) with IRT + conformal prediction + OOD is, functionally, a high-precision confidence filter for pseudo-labeling. Use auto-accepted high-confidence segments as pseudo-labels and human DPO corrections as gold, then run iterative noisy-student self-training: teacher labels unlabeled Sorani audio, apply SpecAugment + speed perturbation (0.9/1.0/1.1) + additive noise ONLY to the student inputs (2025 best practice: augmenting the teacher degrades pseudo-label quality), filter by conformal/agreement confidence to avoid error amplification, retrain. Conformal-risk-control can also give a calibrated 'auto-accept' threshold with a provable WER bound (e.g. WER<X at 80% confidence), which directly upgrades the refinery's auto-accept gate.  
*Tool:* Noisy Student Training + SpecAugment/speed-perturb (torchaudio); Conformal Risk Control for the auto-accept threshold — *Impact:* high - converts the data-curation architecture into measurable accuracy gains, compounding every correction into a better model; differentiates Cortex from every base-model wrapper if the resulting lift is independently verified. — *Effort:* M - reuse refinery confidence signals; add a pseudo-label export + augmentation pass to the LoRA training loop. — <https://arxiv.org/html/2505.24656v2>

## Credible ASR evaluation & public benchmarking for Kurdish/Sorani (Central Kurdish, ckb)

Cortex Speech's biggest credibility gap is "zero published WER/CER despite an eval harness." The fix is cheap and high-leverage: a public, reproducible Central Kurdish (ckb) test set already exists. FLEURS ckb_iq (google/fleurs, CC-BY-4.0, test=922 utts, ~3h) is the single best public, citable test set; the AsoSoft 600-utterance test set (exposed in PawanKrd/asr-ckb-v2) is the de-facto academic Sorani benchmark used by the prior literature (Veisi/Jira WER 13.9% on 43.68h; xls-r-2b+3gram 11.8% on AsoSoft). The ground truth to beat: Meta Omnilingual ASR 7B LLM-ASR reports CER 6.0 on ckb_Arab (FLEURS) with only 59.6h training (per_language_results_table_7B_llm_asr.csv); the 300M CTC that Cortex ships is far weaker. Whisper-large-v3 is catastrophic zero-shot on ckb (~98 WER, Arabic-script substitution failure), so Cortex can credibly beat Whisper. THE decisive move: publish ONE defensible ckb WER/CER number on FLEURS ckb_iq test with a fully reproducible protocol. The non-negotiable methodology detail for Arabic-script Sorani is normalization BEFORE scoring using the AsoSoft normalizer (ZWNJ: "ه"+U+200C -> Kurdish "ە" U+06D5; standardize ک/ی/ؤ; strip Arabic Presentation Forms FB50-FDFF/FE70-FEFF; unify digits) — without this, WER is inflated by 10-30 points of pure orthographic noise and any number is meaningless. Report CER as the primary metric (WER is unstable for an agglutinative, inconsistently-spaced language), with 95% blockwise-bootstrap confidence intervals and a MAPSSWE matched-pair test vs the Whisper baseline. Pin everything (model SHA, dataset revision, jiwer version, normalizer commit) and ship a one-command repro script + HF model-card eval-results YAML. World-class target: CER <= 8 / WER <= 18 on FLEURS ckb_iq for the local 300M after fine-tuning; <= Omnilingual-7B CER 6.0 is the stretch ceiling.

### Recommendations

**Make AsoSoft normalization the mandatory pre-scoring step for Sorani WER/CER (the ZWNJ/Arabic-script pitfall)**  
Arabic-script Sorani WER is dominated by orthographic noise unless you normalize reference AND hypothesis identically before scoring. Use the AsoSoft normalizer (pip install asosoft, Python 3.11+; or the C# AsoSoftLibrary) which: replaces 'ه'+ZWNJ (U+200C) with Kurdish 'ە' (U+06D5); standardizes look-alike letters ڪ/ے/ٶ -> ک/ی/ؤ; strips deprecated Arabic Presentation Forms (U+FB50-FDFF, U+FE70-FEFF); unifies digits and punctuation; normalizes dashes/spaces and removes Unicode control chars. Pitfall to AVOID: do not over-normalize (e.g. stripping all ZWNJ or collapsing Yeh variants beyond the standard) — that hides real errors and makes the number look better than it is; document the exact normalizer commit and apply it symmetrically. Because spacing/affix attachment is inconsistent in Sorani, report CER as the PRIMARY metric and WER as secondary. Wire this into the Rust eval harness via a thin Python sidecar or a Rust port of the rules so the published number and the in-app number match exactly.  
*Tool:* AsoSoft-Library-py (pip: asosoft) — *Impact:* high | without this every WER number is meaningless/inflated 10-30 pts; with it, numbers are defensible and reproducible — this is what separates a real benchmark from marketing — *Effort:* M | integrate asosoft normalizer + symmetric apply in harness, ~2-3 days — <https://github.com/AsoSoft/AsoSoft-Library-py>

**Report WER/CER with 95% blockwise-bootstrap CIs and a MAPSSWE matched-pair test vs Whisper-large-v3**  
A point estimate on 922 utterances is not credible alone. Compute 95% confidence intervals via blockwise bootstrap (Liu et al., Interspeech 2020, arXiv:1912.09508) — block by speaker/utterance to respect within-speaker correlation; ready-made impl: ogunlao/asr_stat_significance (bootstrap + blockwise bootstrap for WER-difference significance). For the headline 'we beat Whisper' claim, run the MAPSSWE matched-pair significance test (p<0.05) between Cortex and Whisper-large-v3 on the SAME utterances. Whisper-large-v3 is zero-shot catastrophic on ckb (~98 WER, Arabic->Arabic/Persian script substitution failure documented for ckb/Pashto/Somali), so beating it is easy and the CI/significance test makes the win rigorous rather than hand-wavy. Publish the per-utterance JSONL of refs+hyps+edits so anyone can recompute.  
*Tool:* jiwer + ogunlao/asr_stat_significance — *Impact:* high | converts a bare number into a statistically defensible claim; pre-empts the obvious 'is this just noise / cherry-picked?' critique — *Effort:* S | jiwer for WER/CER + asr_stat_significance for CI/MAPSSWE, ~1 day — <https://github.com/ogunlao/asr_stat_significance>

## SOTA for ASR data curation, active learning, LLM-as-judge, and uncertainty quantification (2025-2026)

Cortex Speech was previously given an informal high architectural rating for its tiered "Disagreement Refinery," but that opinion was not a product attestation. The system remained unproven: it had no published WER/CER or measured refinery lift, and its offline claim conflicted with a cloud-dependent jury. The 2025-2026 SOTA landscape has converged on a clear playbook that Cortex partially implements but does not yet *prove* or *measure*: (1) confident-learning / data-centric error detection (Cleanlab, now with the TLM trustworthiness score, 3x precision on hallucination detection); (2) hybrid uncertainty+diversity active learning specialized for sequence ASR (length-normalized path probability + entropy + clustering); (3) bias-aware LLM-as-judge where STYLE bias (0.76-0.92) — not position bias (<=0.04) — is the dominant failure, mitigated best by chain-of-thought forcing (+7.2pp) and combined-budget prompting (+11.2pp on Claude Sonnet 4), with cross-family ensembles for high stakes; (4) IRT applied to the *judges themselves* (IRT-Judge, 2026) to model judge ability/discrimination, exactly the latent-trait framing Cortex already uses for models; (5) conformal *risk control* (MAPIE v1, TorchCP, crepes) for distribution-free coverage guarantees, with TorchCP being the GPU/PyTorch-native choice and MAPIE's 2026 roadmap explicitly adding LLM-as-Judge risk control; (6) preference optimization moving past vanilla DPO to KTO/ORPO/SimPO, with token-level DPO now demonstrated for ASR. Competing platforms (Argilla 2.x on HF, Label Studio, Prodigy, Cleanlab Studio, Snorkel Flow, Encord, Scale/Surge) own distribution and auditability. Cortex's combination may be differentiated, but no superiority claim is valid until measured against those products and backed by reproducible evidence. The single highest-leverage move is not more features — it is a published WER/CER scorecard plus a measured "label-quality lift" benchmark proving the refinery beats raw OmniASR output by X CER points at Y% human effort.

## 2026 best practices for a world-class Rust + Tauri v2 + Svelte 5 codebase — turning Cortex Speech's "engineering rigor 8" into an unimpeachable 10 via concrete, enforced CI gates

Cortex already has the hard parts most projects skip: a deny.toml, 5 cargo-fuzz targets (cache/diff/features/normalizer/validation), 3 criterion benches, proptest with checked-in regressions, 360 tests, and a two-job Windows/Linux CI ("Release Gate") plus a release matrix. That is genuinely 8/10. But the gates that exist are NOT actually wired: fuzz targets and benches are never run in CI, there is no mutation testing, no SBOM, no build provenance/SLSA attestation, no code signing, no cargo-vet, no OpenSSF Scorecard, no accessibility gate, no observability (tracing/OTel), and — most damning — the repo is not under git at all, so none of release engineering applies yet. The "13 production unwraps" claim is also unverifiable/contradicted by source (export.rs alone has 134 unwrap() occurrences; even if mostly in #[cfg(test)], the headline number needs a clippy-enforced proof). The path to 10 is not new infrastructure — it is converting the latent capability into enforced, required, merge-blocking gates and publishing the evidence. Concretely: (1) git init + signed tags + branch protection TODAY; (2) wire the existing 5 fuzz targets into a nightly cargo-fuzz job + a fast PR smoke (30s/target); (3) add cargo-mutants --in-diff as a PR gate to prove the 360 tests actually catch bugs; (4) add provenance via actions/attest-build-provenance (SLSA L2 out-of-box) + cargo-cyclonedx SBOM + cargo-auditable embedded SBOM on every release binary; (5) sign Windows (Azure Trusted Signing / azuresigntool) and notarize macOS in the existing release matrix; (6) add OpenSSF Scorecard + pin every Action to a full SHA (the tj-actions attack of 2025 makes this non-negotiable); (7) add @axe-core/playwright to the existing Playwright e2e for a WCAG 2.2 AA gate; (8) gate criterion benches against a baseline so latency can't silently regress; (9) instrument Rust with tracing + an optional OTel exporter so the refinery's tier decisions are observable; (10) enforce the unwrap budget with clippy. Each maps to a single named tool and a single CI job. Sources are 2025-2026.

### Recommendations

**Put the repo under git, sign tags, and enable branch protection with required status checks — this is the prerequisite for every other gate**  
Cortex is not under version control, which silently nullifies the entire 'release engineering' axis: no signed tags, no provenance, no Scorecard, no PR-diff gates can exist without git. Step 1: git init, commit, push to a private GitHub repo. Step 2: configure signed tags (git config tag.gpgSign true, or use Sigstore gitsign for keyless OIDC signing so a single dev doesn't manage long-lived keys). Step 3: protect main: require the existing 'Windows Release Gate' check, require PR review (even self-review via a second machine or a CODEOWNERS bot), disallow force-push, require linear history. Step 4: adopt Conventional Commits (you already have commitlint.config.js + .husky) and add release-please or semantic-release to derive versions/changelog from commit history so CHANGELOG.md stops being hand-maintained. Until git exists, 'distribution/adoption 0' and 'trust/proof 2' cannot move.  
*Tool:* git + Sigstore gitsign (keyless tag signing) + release-please (googleapis/release-please-action) — *Impact:* high — unblocks all of release engineering, provenance, and Scorecard; converts a structural gap (the single biggest credibility hole) into a checkbox. Without git, 5 of the 10 gates below are impossible. — *Effort:* S — under a day. git init + GitHub repo + branch protection rules + add release-please action. — <https://github.com/sigstore/gitsign>

**Wire the 5 existing cargo-fuzz targets into CI: a fast PR smoke + a nightly long campaign with corpus persistence**  
You already have src-tauri/fuzz/fuzz_targets/{cache,diff,features,normalizer,validation}.rs — they are dead weight because nothing runs them. cargo-fuzz (libFuzzer backend) is still the de-facto Rust fuzzer in 2026; recent releases added --codegen-units 1 (default, best throughput), --strip-dead-code, and --disable-branch-folding for cleaner coverage. Add two jobs: (a) PR smoke — for each target run `cargo +nightly fuzz run <target> -- -max_total_time=30 -runs=0` (~2.5 min total) so regressions in the audio/diff/normalizer parsers fail the PR; (b) nightly — `-max_total_time=900` per target on a schedule, with the corpus cached via actions/cache keyed on target name so coverage accumulates across runs, and any crash uploaded as an artifact + auto-filed issue. ASan is on by default (keep it — you have unsafe FFI to sherpa-onnx/onnxruntime.dll, exactly where memory bugs hide). Consider migrating the harnesses to bolero so the SAME #[test] body runs as a unit test, a proptest, AND a libFuzzer/AFL++ target via one unified interface — that collapses your proptest + fuzz duplication.  
*Tool:* cargo-fuzz (libFuzzer) + optionally bolero for unified proptest/fuzz harnesses; AFL++ only if you need a second engine for differential coverage — *Impact:* high — the normalizer/diff/audio parsers ingest untrusted Kurdish text + arbitrary audio bytes; fuzzing is the single highest-value gate for a transcription tool. Turns existing-but-unused harnesses into a live safety net and is direct evidence for 'engineering rigor'. — *Effort:* M — harnesses already exist. ~1 day to add the two jobs + corpus caching; +1 day if migrating to bolero's unified interface. — <https://rust-fuzz.github.io/book/cargo-fuzz.html>

**Add cargo-mutants --in-diff as a required PR gate to prove the 360 tests actually catch bugs (not just execute lines)**  
360 tests sounds strong but coverage % only proves lines RAN, not that a wrong result would be caught. cargo-mutants (v27.1.0, June 2026, actively maintained, zero-config, works with cargo-nextest) injects bugs — swaps operators, replaces return values with Default — and fails if no test notices. Run it incrementally so it's fast enough for PRs: `git diff origin/main...HEAD > pr.diff` then `cargo mutants --in-place --in-diff pr.diff -- --all-targets` only mutates changed code (seconds-to-minutes, not the whole tree). Add a weekly FULL run with `--shard k/N` across a matrix to parallelize the entire crate and publish the surviving-mutant count as a tracked metric. This is the gate that converts 'we have lots of tests' into 'our tests are provably effective' — exactly the evidence 'trust/proof 2' needs. Target: zero surviving mutants in the refinery scoring (IRT/conformal/OOD) and diff/normalizer modules, where a silently-wrong number corrupts the dataset.  
*Tool:* cargo-mutants v27.1.0 (with cargo-nextest as runner) — *Impact:* high — directly attacks the gap between test quantity and test quality. For a data-curation tool whose output trains models, an undetected scoring bug is catastrophic; mutation testing is the only gate that catches 'test asserts nothing meaningful'. — *Effort:* M — `cargo install --locked cargo-mutants`, add PR job with --in-diff (~half a day), then iterate killing surviving mutants in core modules (ongoing). — <https://mutants.rs/pr-diff.html>

**Generate + publish build provenance (SLSA), a CycloneDX SBOM, and embed an auditable SBOM in every release binary**  
Three complementary artifacts, all free on GitHub: (1) actions/attest-build-provenance@v2 in release.yml emits a signed in-toto SLSA provenance attestation per artifact (SLSA Build L2 out-of-the-box via public-good Sigstore; the build+attest run in the same job so true L3 needs the slsa-github-generator BYOB reusable workflow if you want to claim L3). Consumers verify with `gh attestation verify <file> --repo <owner>/<repo>` or slsa-verifier. (2) cargo-cyclonedx produces a CycloneDX 1.6 SBOM of all Rust deps; attach it to the GitHub Release and attest it too. (3) Build the shipping binary with `cargo auditable build --release` so the dependency list is embedded IN the binary — Microsoft and 6 Linux distros do this — letting anyone run `cargo audit bin cortex-speech.exe` years later. Net effect: a downloaded Cortex binary is cryptographically traceable to the exact commit + workflow that built it, and its full dependency tree is inspectable. This is concrete, verifiable 'trust/proof'.  
*Tool:* actions/attest-build-provenance@v2 + cargo-cyclonedx + cargo-auditable (verify with slsa-verifier / gh attestation verify) — *Impact:* high — moves 'trust/proof' from a marketing claim to a machine-verifiable fact. For an offline tool handling sensitive speech data, downloadable provenance is a genuine adoption differentiator vs Whisper/Dragon. — *Effort:* M — ~1 day. attest-build-provenance is ~6 lines; cargo-cyclonedx + cargo-auditable are one install + one build-command swap each. — <https://github.com/actions/attest-build-provenance>

**Sign + notarize release binaries: Azure Trusted Signing for Windows, Developer ID notarization for macOS, in the existing release matrix**

For Windows, Azure Trusted Signing (formerly Azure Code Signing) is now the recommended path — no $300+/yr EV cert + USB token; you get a cloud-managed cert and sign in CI with azuresigntool, wired via Tauri's signCommand in tauri.conf.json's bundle config. **Add OpenSSF Scorecard as a required check and pin every GitHub Action to a full commit SHA**  
Your workflows pin to floating tags (actions/checkout@v4, dtolnay/rust-toolchain@stable, softprops/action-gh-release@v2). The March 2025 tj-actions/changed-files supply-chain compromise (a retagged tag exfiltrated secrets across 23k+ repos) makes SHA-pinning mandatory: rewrite every `uses:` to `owner/action@<40-char-sha> # vX.Y.Z`. ### Risks
- The '13 production unwraps' headline is not enforced by any gate and is contradicted by source (export.rs has 134 unwrap() occurrences, commands.rs 57). Until clippy::unwrap_used is denied in non-test code, this number is unverifiable and weakens the rigor claim rather than supporting it — fix the gate before quoting the number.
- Self-hosted GitHub-Actions provenance is only SLSA Build L2, not L3, because build and attestation run in the same job. Do not claim 'SLSA L3' until you migrate to the slsa-github-generator BYOB reusable workflow; over-claiming the level is itself a trust hole.
- cargo-mutants on the full tree can take hours and is the #1 cause of teams abandoning mutation testing. Ship --in-diff (PR) first and shard the full run weekly; a slow mandatory gate will get disabled and you'll lose the benefit entirely.
- Floating action tags (checkout@v4, action-gh-release@v2) are an active, exploited attack vector after the March 2025 tj-actions compromise. Until every uses: is SHA-pinned, the supply-chain posture is materially worse than the deny.toml suggests — this is the most urgent single hardening item alongside git.
- Windows code signing via Azure Trusted Signing requires an established Azure tenant + identity-validated subscription; the validation can take days/weeks and may need a registered business identity. Start the Azure Trusted Signing onboarding early — it is the long-pole dependency for a signed Windows release.

## Kurdish (Sorani/Central Kurdish) NLP & Speech for Cortex Speech

The Central Kurdish (ckb) ASR field is small, concentrated in a handful of groups (AsoSoft / Aso Mahmudi, Sina Ahmadi's KLPT+CORDI ecosystem, Hossein Hassani's Kurdish-BLARK at UKH, Hadi Veisi's lab), and now has a clear performance bar. Meta's Omnilingual ASR (arXiv 2511.09690, Apache-2.0) reports CER 6.0 on ckb_Arab from only 59.6h of training data with the 7B-LLM model — the exact model family Cortex already wires (OmniASR/Omnilingual CTC 300M/1B). The best published Central Kurdish system (arXiv 2406.02561, Hawkar Omar et al.) reaches WER 10.0% on validation / 11.8% on the AsoSoft test set using xls-r-2b + 3/4-gram LM; the KUTED corpus paper (arXiv 2604.00613) shows fine-tuned ASR dropping WER 21.6 -> 8.6 with proper orthographic normalization. This means two things for Cortex: (1) its accuracy "2/10" is a measurement gap, not a capability ceiling — the underlying model is near-SOTA and Cortex just needs to publish CER/WER on AsoSoft + CORDI test sets to jump to a credible 6-7/10; (2) the single biggest accuracy lever for Kurdish is Arabic-script normalization, where mis-handled ZWNJ/heh/yeh/kaf variants and digit forms silently inflate CER by double digits. Cortex should (a) adopt a rigorous, documented Sorani normalizer aligned to W3C/r12a + AsoSoft/KLPT rules and apply it identically to references, hypotheses, and DPO pairs; (b) ingest the openly-licensed CORDI (100h+, CC BY-SA, 6 Sorani dialects) and AsoSoft corpora to become dialect-aware and to publish the field's first per-dialect Sorani leaderboard; (c) build community credibility by partnering with AsoSoft, Sina Ahmadi, UKH, and Mozilla Common Voice (122h Sorani) and contributing its Disagreement Refinery as a data-curation engine — its actual 10/10 strength — back to the ecosystem. Dialect breadth (Kurmanji kmr, Hawrami, Southern/Laki) is a credibility multiplier but should be sequenced after Sorani is definitively nailed.

### Recommendations

**Adopt a documented, codepoint-exact Sorani normalizer and apply it identically to refs, hypotheses, and DPO pairs**  
Arabic-script normalization is the #1 silent CER inflator for ckb. Implement a canonical Sorani normalizer in Rust with an explicit, tested codepoint map: AE vowel must be U+06D5 (map the legacy HEH+ZWNJ hack U+0647 U+200C -> U+06D5); Sorani yeh U+06CC (map Arabic yeh U+064A and NFD U+064A+U+0654 -> U+06CC); Sorani kaf/keheh U+06A9 (map Arabic kaf U+0643 -> U+06A9); rreh U+0695 for word-initial/strong r (AsoSoft rule: word-initial ر -> ڕ); long-u وو vs و; oe U+06C6, yeh-with-tail/ee U+06CE (NFD-normalize U+06CE -> U+064A+U+0654 then recompose); replace deprecated Arabic Presentation Forms (U+FB50-FDFF, U+FE70-FEFF) with base letters; strip Private-Use-Area glyphs. Run NFC after mapping. CRITICAL: the same normalizer must be applied to (a) Gemini reference transcripts, (b) OmniASR hypotheses, (c) human corrections before DPO export, and (d) eval references — otherwise WER/CER are measuring orthography noise, not acoustics. The KUTED paper shows this normalization alone moved WER from 21.6 to 8.6.  
*Tool:* Port AsoSoft normalizer rules + KLPT preprocess (Python, pip install git+https://github.com/sinaahmadi/klpt.git, CC BY-SA 4.0) into native Rust; validate against W3C/r12a Sorani notes — *Impact:* high — directly recovers double-digit CER and makes every published number trustworthy; gates the entire 'Proven accuracy' and 'Trust/proof' scores — *Effort:* M — ~1-2 weeks: a few hundred lines of Rust mapping + a property-test suite over the codepoint table; reuse existing proptest infra — <https://r12a.github.io/scripts/arab/ckb.html>

**Publish CER/WER on the AsoSoft test set and CORDI — the field's de-facto benchmarks — to convert the eval harness into proof**  
Cortex has an eval harness but zero published numbers; meanwhile competitors have concrete bars. Run the existing OmniASR CTC 300M and 1B through Cortex's harness on: (1) the AsoSoft test set (the standard ckb benchmark — published systems report WER ~11.8-13%), and (2) a held-out CORDI split for per-dialect CER. Report CER as the PRIMARY metric for Kurdish (WER is unstable due to joined/separated-word variation — KUTED documents the same word appearing in 4+ written forms). Reference targets: OmniASR-7B-LLM hits CER 6.0 on ckb_Arab; the 300M CTC will be higher (realistically CER ~8-12). Put a one-page METHODS + a results table in the repo and README. This single action plausibly moves Proven-accuracy from 2 to 6 and Trust/proof from 2 to 6 with no model changes.  
*Tool:* AsoSoft test set (github.com/AsoSoft); CORDI (github.com/sinaahmadi/CORDI, CC BY-SA 4.0); jiwer-equivalent CER/WER already in harness — *Impact:* high — turns the strongest hidden asset (8/10 engineering rigor) into public credibility; cheapest possible jump on the two lowest non-zero scores — *Effort:* S — days: data is already public; the harness exists. Mostly download, split, run, write up — <https://arxiv.org/pdf/2406.02561>

**Ingest CORDI to become the first dialect-aware Sorani tool and publish a per-dialect leaderboard**  
CORDI (Sina Ahmadi) is uniquely valuable: 100+ hours, 186,038 utterances across 6 Central Kurdish varieties (Sulaymaniyah/Babani, Sanandaj/Ardalani, Mahabad/Mukri, Erbil/Hewler, Sardasht, Kalar), with per-utterance gender/age/dialect metadata, .ogg audio + .srt, under CC BY-SA 4.0 — directly ingestible by Cortex's curation pipeline. Use it to (a) report CER per dialect (no one has published this — instant differentiation), (b) feed the Disagreement Refinery to surface where OmniASR systematically fails by dialect, and (c) build dialect-balanced fine-tuning/DPO sets. Sorani has real sub-dialect spelling/pronunciation divergence; a tool that quantifies and handles it becomes 'the definitive Kurdish speech tool' in a way single-accuracy-number competitors cannot match. Sequence Kurmanji (kmr) AFTER Sorani is nailed — OmniASR already does kmr_Arab at CER 1.2, so kmr is a fast follow, not a prerequisite.  
*Tool:* CORDI corpus (github.com/sinaahmadi/CORDI); optionally KASET (LDC2024S01, restricted) for cross-corpus eval — *Impact:* high — converts Language-breadth (1/10) into a defensible moat via dialect depth rather than chasing many languages shallowly — *Effort:* M — ingest + dialect-tagging plumbing + per-dialect eval reporting; audio is .ogg so a decode step is needed — <https://github.com/sinaahmadi/CORDI>

**Build a Sorani pronunciation lexicon + G2P for forced alignment, confidence calibration, and FLAC-correct exports**  
Use the AsoSoft Kurdish-G2P dataset (5000 most-frequent words + 5041 Wergor words, IPA with syllable boundaries, Sorani, e.g. 'ئازادی -> .ʔa.za.dî') to build a pronunciation lexicon. Three payoffs for Cortex: (1) forced alignment / phone-level timing improves segment boundaries feeding the tiered jury and produces cleaner training clips; (2) phoneme-aware confidence sharpens the T0 gate and conformal/IRT calibration (a hypothesis that is graphemically wrong but phonemically plausible is a known ASR failure mode worth down-weighting, not escalating); (3) it underpins a phoneme/character-level error analysis in the eval report (cf. arXiv 2604.18204 phoneme-level ASR analysis). Pair with the AsoSoft Central-Kurdish-Spelling-dataset to auto-flag systematic mis-spellings before DPO export so preference pairs teach acoustics, not orthography noise.  
*Tool:* AsoSoft Kurdish-G2P-dataset (github.com/AsoSoft/Kurdish-G2P-dataset); Central-Kurdish-Spelling-dataset; align with sherpa-onnx or a CTC-segmentation pass — *Impact:* medium — compounding gains for the Refinery's calibration and export quality; also unblocks the unimplemented FLAC export with correctly-segmented clips — *Effort:* M — lexicon build is small; G2P-for-OOV and alignment integration is the work — <https://github.com/AsoSoft/Kurdish-G2P-dataset>

**Partner with AsoSoft, Sina Ahmadi, UKH/Kurdish-BLARK and Mozilla Common Voice for data, credibility, and distribution**  
Cortex's fatal non-technical gaps are Distribution/adoption (0) and Trust (2), solvable by embedding in the existing Kurdish-NLP community rather than competing with it. Concrete moves: (1) AsoSoft (Aso Mahmudi) — align Cortex's normalizer to AsoSoftLibrary, cite it, contribute Rust port back; (2) Sina Ahmadi — CORDI/KLPT author, the central connector (awesome-kurdish list); getting Cortex listed there is free distribution to every Kurdish-NLP researcher; (3) Dr. Hossein Hassani (University of Kurdistan Hewler / Kurdish-BLARK) — academic validation + student annotators + a co-authored eval paper; (4) Mozilla Common Voice ckb (122h Sorani, led by Davud Kakaie; Mozilla 'Our Voices' award) — Cortex's Disagreement Refinery is exactly the QA/validation layer Common Voice lacks; offer it as a community validation tool and run a targeted Sorani recording campaign to grow the corpus. Position Cortex's 10/10 data-curation refinery as a *contribution to the commons*, which simultaneously earns adoption and sources more training data. Also: get Cortex under git + a public repo first — it is currently unversioned, which blocks every one of these partnerships.  
*Tool:* AsoSoft (github.com/AsoSoft); awesome-kurdish (github.com/sinaahmadi/awesome-kurdish); Kurdish-BLARK (kurdishblark.github.io); Mozilla Common Voice ckb + Mozilla Data Collective — *Impact:* high — only realistic path off 0/10 distribution and to durable trust; also a renewable data pipeline — *Effort:* L — relationship-building + a public, versioned repo + at least one co-authored benchmark/paper; months not weeks — <https://github.com/sinaahmadi/awesome-kurdish>

**Resolve the offline-first contradiction by making Gemini optional and adding an offline Sorani reference path**  
Marketing says offline-first but the jury depends on cloud Gemini for reference transcripts — a real trust and adoption blocker for Kurdish users (data-sovereignty sensitivity, intermittent connectivity in the region). Replace the hard Gemini dependency with a tiered, fully-local fallback: use a second local model as the cross-checker — e.g. run OmniASR 1B (or 7B-CTC if hardware allows) as the 'reference' against the 300M 'candidate', so the Disagreement Refinery's T0->T2 escalation works with zero network. OmniASR is Apache-2.0 and ships CTC 300M/1B/3B/7B + LLM variants, so a stronger local model is a drop-in. Keep Gemini as an opt-in accuracy booster, not a requirement, and label it clearly in the UI/i18n (EN/CKB). This makes 'offline-first' true and turns the Refinery into a genuinely local, sovereign curation engine.  
*Tool:* Omnilingual ASR CTC 1B/7B (facebookresearch/omnilingual-asr, Apache-2.0) as local cross-checker via sherpa-onnx; Gemini demoted to optional — *Impact:* medium — removes a credibility-killing contradiction and a hard cloud dependency; strengthens the privacy story that matters to this user base — *Effort:* M — wire a second local model as reference in the jury; the 1B is already 'wired' per scorecard — <https://github.com/facebookresearch/omnilingual-asr>
